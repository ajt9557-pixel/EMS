EMPLOYEE MANAGEMENT SYSTEM — PSEUDOCODE
(React front-end + Express/Node/MongoDB back-end)


1. App Routing

When the app loads, check the current URL path.

If the path is "/" or something unrecognized, show the Login page.
If the path is "/login", show the Login page.
If the path starts with "/admin-dashboard" or "/employee-dashboard", hand off to the PrivateRoute check.

PrivateRoute(route):
Look for a saved token in storage.
If there isn't one, redirect to the Login page and stop here.
Otherwise, call GET /api/auth/verify with that token.
If the response says the token is invalid or expired, log the user out.
If it's valid, move on to the RoleBaseRoute check using the returned user.

RoleBaseRoute(route, user):
Work out which role the route needs — admin for "/admin-dashboard" routes, employee otherwise.
If the user's role doesn't match, show the Access Denied page.
If it matches, show the Admin Dashboard for admins or the Employee Dashboard for everyone else.


2. Authentication

LoginPage():
Show a form with email, password, and a "remember me" checkbox.

On submit:
If either email or password is blank, show an error banner asking for both fields, and stop.
Otherwise show a loading indicator and call POST /api/auth/login with the email and password.
If login fails, hide the loading indicator, show the error message, and stop.
If it succeeds, take the returned token and user object.
If "remember me" was checked, save the token to localStorage; otherwise save it to sessionStorage.
Save the user to AuthContext and hide the loading indicator.
Finally, navigate to the Admin Dashboard if the user is an admin, or the Employee Dashboard otherwise.

Logout():
Delete the token from storage, clear AuthContext, and navigate back to the Login page.


3. Admin Dashboard

AdminDashboard():
Show the layout with a sidebar, navbar, and logout button, along with links to Summary, Employees, Departments, Leaves, Salary, and Settings.
Call GET /api/admin/summary and display the results as stat cards — total employees, total departments, monthly salary, and leave stats.


4. Employee Module (CRUD)

EmployeeList():
Call GET /api/employee and display the results in a table with profile photo, name, email, department, salary, and an actions column.
As the user types a search keyword, filter the list down to employees whose name contains it.
Clicking "Add New Employee" opens the AddEmployee flow.
Clicking "Edit" on a row navigates to that employee's edit page.
Clicking "Delete" on a row triggers DeleteEmployee for that employee.

AddEmployee():
Load the department list from GET /api/department to populate a dropdown.
Show a form for name, email, password, employee ID, date of birth, gender, marital status, designation, department, salary, role, and photo.

On submit:
Package the fields and photo into a multipart form and call POST /api/employee/add.
On the backend, the password gets hashed with bcrypt, and the system checks whether the email or employee ID is already in use.
If it's a duplicate, an error comes back and the form shows it so the user can fix it.
If not, a new User document is saved for login credentials, followed by a new Employee document holding the profile details.
Once that succeeds, navigate back to the employee list.

DeleteEmployee(employeeId):
Show a confirmation dialog. If the user cancels, do nothing.
If they confirm, call DELETE /api/employee/{employeeId}, which removes both the User document and the Employee document, then refresh the list.


5. Department Module (CRUD)

DepartmentList():
Call GET /api/department and display the results in a table with a row number, department name, and actions.
Clicking "Add New Department" opens the AddDepartment flow.
Clicking "Edit" opens EditDepartment for that department.
Clicking "Delete" triggers DeleteDepartment for that department.

AddDepartment():
Show a form for department name and description.

On submit, if either field is empty, show an error asking for the missing fields and stop.
Otherwise call POST /api/department/add with the form data, then navigate back to the department list.

EditDepartment(departmentId):
Fetch the department with GET /api/department/{departmentId} and prefill the form with its current values.
On submit, call PUT /api/department/{departmentId} with the updated data, then navigate back to the list.

DeleteDepartment(departmentId):
Show a confirmation dialog. If cancelled, do nothing.
If confirmed, call DELETE /api/department/{departmentId} and refresh the list.


6. Leave, Salary, and Settings (planned modules)

ApplyLeave(employeeId, leaveDetails):
Call POST /api/leaves with the employee ID and leave details, setting the status to "pending".

AdminReviewLeaves():
Call GET /api/leaves and display them with Approve and Reject buttons.
Approving a leave calls PUT /api/leaves/{leaveId} with status set to "approved"; rejecting sets it to "rejected".

ViewSalary(employeeId):
Call GET /api/salary/{employeeId} and display the gross pay, deductions, and net pay, along with a "Print payslip" button.

UpdateProfile(newProfileData):
Call PUT /api/users/me with the updated profile fields.

ChangePassword(oldPassword, newPassword):
Call PUT /api/users/me/password with the old and new passwords.


7. Employee Dashboard

EmployeeDashboard():
Show a simple placeholder dashboard.
Clicking "My Leaves" calls GET /api/leaves/my and displays the employee's own leave requests with their current status.


8. Backend API Flow (Express + MongoDB)

For any request that comes in to /api/*:

Pull the Bearer token out of the request headers.
If there isn't one, respond with 401 "No token".
Otherwise verify it against the JWT secret.
If it's invalid or expired, respond with 401 "Invalid or expired token".
If it checks out, look up the user by the decoded ID.
If no matching user exists, respond with 404 "User not found".
Once the request is authenticated, pass it along to the matching controller.
The controller talks to the relevant Mongoose model — User, Employee, Department, or Leave — to read or write MongoDB.
Whatever comes back gets sent to the front end as a JSON response.


A few notes: authentication, employee CRUD, department CRUD, and the admin layout with summary cards are fully built out. Leaves, salary, settings, the employee dashboard's detail view, and the employee edit page route are still stubbed in as planned work. Passwords are always hashed with bcrypt before being saved, and deleting an employee cascades to remove their linked User document too.
